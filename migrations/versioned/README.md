# Версионированные миграции

Каждый файл миграции называется `<ID>.php`, где ID имеет вид
`ГГГГММДДЧЧММ_краткое_имя`, и возвращает ровно пять полей:

```php
<?php

use HScript\Database\Connection;

return array(
    'id' => '202609071200_example',
    'from' => '1.0.0',
    'to' => '1.1.0',
    'classification' => 'backup-required',
    'up' => static function (Connection $database): void {
        // Повторный запуск после обрыва должен быть безопасным.
    },
);
```

После публикации ID и содержимое файла не меняются: SHA-256 проверяется при
подготовке официального архива и фиксируется в таблице `SchemaMigrations`. Исправление уже выпущенной
миграции оформляется новым файлом. DDL MySQL может не участвовать в транзакции,
поэтому обработчик обязан проверять уже выполненные шаги и допускать повтор.

Миграции выполняются только общим сервисом обновления под advisory lock. Старый
установщик и `APP_AUTO_INSTALL` для этого не используются.

Перед обновлением оператор может просмотреть неизменяемый план:

```sh
APP_DOMAIN=example.com php bin/update.php plan 1.0.1
```

В Docker после запуска нового точного image tag миграция выполняется действием
обновления в `/_cfg?update` или командой `php bin/update.php migrate-bundled`.
Для shared hosting сначала подготавливается проверенный официальный архив через
Configurator/`bin/update.php prepare`, затем применяется полученный prepared ID.
Общий сервис сам создаёт и проверяет SQL backup для
`classification=backup-required`; `code-only` не запускает миграции и не создаёт
лишний SQL backup.

Если процесс остановился после создания run, новый запуск не создают. Состояние
проверяют через `php bin/update.php status`, затем продолжают сохранённый run
командой `php bin/update.php resume <run-id>`. Уже завершённые шаги и checksum
проверяются повторно, а несовместимое частичное состояние блокирует продолжение.
SQL restore сначала испытывают в отдельной пустой базе через
`php bin/backup.php restore`; целевая база и её подтверждение должны совпасть.

Миграция `202609101200_telemetry_ingestion` переводит schema `1.0.0` в `1.0.1`
и относится к `backup-required`: она добавляет строгий telemetry ingestion,
bounded IP/domain history, rejection counters и индексы списков collector.

Миграция `202609221200_domain_proof` переводит schema `1.0.1` в `1.0.2`
для CMS `1.0.5` и имеет класс `backup-required`. Добавляются поля одноразового
HTTPS challenge и срока подтверждения домена; существующие записи не удаляются.
После запуска нового образа выполните обновление через `/_cfg?update`, затем
ручную `test:staging-reconciliation` именно в pipeline этого образа.
`APP_AUTO_INSTALL` оставьте `0`. Публиковать старый образ поверх изменённой схемы
без проверенной процедуры восстановления нельзя.

Первое подтверждение выполняется при следующей успешной регистрации/отчёте.
Маршрут `GET /api/v1/installations/domain-proof` должен быть доступен извне по
HTTPS без Authelia, CAPTCHA, редиректов и кеширования. Он возвращает только
временный challenge, installation ID, домен и срок действия, но не Bearer token.
Коллектор сам вызывает этот точный маршрут с проверкой TLS и закреплённым
публичным IP. Срок подтверждения — 7 дней, обновление — в последние сутки
при отправке отчёта. Смена домена аннулирует подтверждение.
DNS `mismatch` при отдельном nginx/CDN остаётся диагностикой: для публичных
self-reported агрегатов достаточно DNS `matched` **или** действующего HTTPS
подтверждения. Финансовые показатели от этого не становятся проверенными.
