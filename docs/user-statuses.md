# Статусы пользователей

Черновик для последующего переноса в пользовательскую и административную документацию.

| Код | Название в админке | Назначение |
|-----|--------------------|------------|
| `0` | Не активен | Аккаунт создан, но e-mail ещё не подтверждён. Обычная авторизация запрещена с сообщением о необходимости подтверждения. |
| `1` | Активен | Полностью активный аккаунт. Доступны авторизация и штатные пользовательские операции. |
| `2` | Наказан | Временная блокировка до даты из поля `uBTS` («Забанен до»). До указанного времени авторизация запрещена. При первой попытке входа после окончания срока движок автоматически меняет статус на `1` и очищает `uBTS`. |
| `3` | Заблокирован | Бессрочная блокировка. Авторизация запрещена, дата `uBTS` не используется, автоматического восстановления нет. |
| `4` | Резерв | Зарезервированный legacy-статус без законченной бизнес-логики. Авторизация напрямую его не запрещает, но значительная часть запросов принимает только статус `1` или статусы `1`/`2`, поэтому использовать статус `4` нельзя до определения и реализации его поведения. |

## Формат срока блокировки

Поле «Забанен до» заполняется в формате `ДД.ММ.ГГГГ ЧЧ:ММ`, например `25.07.2026 18:30`. Значение интерпретируется в настроенном часовом поясе сайта и сохраняется в `Users.uBTS` как UTC-метка формата `YYYYMMDDHHMMSS`.

Поле имеет смысл только при статусе `2`. Для статусов `0`, `1`, `3` и `4` оно не влияет на обычную авторизацию.

## Важные технические особенности

- Вход из админ-панели от имени пользователя вызывает авторизацию с административным обходом проверки статуса.
- Некоторые финансовые проверки считают допустимыми пользователей со статусами `1` и `2`, хотя пользователь со статусом `2` не может самостоятельно войти до окончания наказания.
- Серверная проверка обязательности и корректности `uBTS` для статуса `2` пока отсутствует; администратору необходимо указывать корректную будущую дату.
